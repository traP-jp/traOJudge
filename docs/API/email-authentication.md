# メール確認後に登録・ログインへ分岐する

登録画面・ログイン画面のどちらから始めても、メール確認までは登録の有無を明かさない。HTTPの入出力スキーマと値の例は[OpenAPI定義](front_back.yaml)を参照する。

## 1. 本人確認メールを要求する

登録画面は `POST /api/v1/auth/email/registrations`、ログイン画面は `POST /api/v1/auth/email/sessions` を使い、メールアドレスを送る。どちらも登録の有無によらず同じ `202 Accepted` と受付情報を返し、利用者やログインセッションはまだ作らない。メール本文やリンク形式でも登録の有無を示さない。

## 2. メールを確認する

メールのリンクを開いたWebUIが `POST /api/v1/auth/email/verifications` に本人確認トークンを送る。リンクのGETだけではトークンを消費しない。

有効なトークンなら `200 OK` を返し、ここで初めて登録の有無に応じて分岐する。

- 登録済みならログイン状態とセッションCookieを返す。
- 未登録なら登録用トークンを返して表示名の入力へ進む。この段階では利用者もセッションも作らない。

本人確認トークンは発行から30分間有効で、一度だけ使える。未登録の場合に返す登録用トークンも元の有効期限を引き継ぎ、期限を延長しない。不正・期限切れ・使用済みのトークンでは、登録の有無を開示せず、セッションや登録用トークンを発行しない。

## 3. 再送する

登録画面とログイン画面のどちらから再送しても、新しい本人確認要求を受け付けた時点で、同じメールアドレス向けに以前発行した未使用の本人確認トークンを失効させる。最新のメールにあるリンクだけが有効で、再送後に旧リンクを確認APIへ送ると `422 Unprocessable Content` となる。登録の有無は開示せず、登録・ログインも成立しない。すでに本人確認を終えて発行された登録用トークンは、再送では失効せず、元の有効期限まで使える。再送はすでに発行済みのログインセッションに影響しない。

新しいリンクの有効期限はその発行から30分とする。メール配送はキューへの依頼であり、`202 Accepted` は配送完了を意味しない。再送要求を受け付けた後にメールが届かない場合も旧リンクは失効しているため、もう一度再送を依頼する。

## 4. 未登録の場合だけ登録を完了する

表示名を入力し、`POST /api/v1/auth/email/registrations/complete` に登録用トークンと表示名を送る。検証に成功すると利用者と `standard-user` を作成し、登録用トークンを一度だけ消費して `201 Created` とセッションCookieを返す。

登録用トークンの発行後にそのメールが登録済みになった場合は `409 Conflict` とし、既存利用者を上書きしたり重複作成したりしない。メール本人確認トークンを登録完了APIへ直接渡しても登録できない。

## 共通の条件

- POSTではブラウザが付けるOriginとWebUIの公開Originとの完全一致を検証する。
- セッションCookieは `HttpOnly`・`Secure`・`SameSite=Lax` とし、有効なセッションでアクセスするたびに期限を90日後まで延長する。
- トークンを含むメールやAPI応答をログへ記録しない。本人確認後の応答はキャッシュしない。

メールアドレス変更の確認リンクは、本人とメール変更目的に紐付く別のトークンとして扱う。新しい確認トークンが発行された場合は、その本人の以前の未使用のメール変更トークンを失効させる。変更先が使用済みで新しいトークンを発行しない場合は、以前のトークンを失効させない。

対応するシナリオは[メールで利用登録する](../requirements/scenarios/authentication/register.md)と[ログイン・ログアウト](../requirements/scenarios/authentication/sign-in-and-out.md)に記す。
