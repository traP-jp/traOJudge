# 問題のDB基盤

解説から問題を実際に参照できるようにするための最小基盤。問題の本文・版・採点設定や問題作成APIは後続で追加する。

## 保存する情報

| 列 | 型 | 用途 |
| --- | --- | --- |
| `id` | UUID | 問題の識別子。主キー |
| `created_by_user_id` | UUID、NULL可 | 作成者。既存の作成者不明な問題はNULLのまま保持 |
| `visibility` | TEXT | `public` / `private`。省略時は `private` |
| `deleted_at` | TIMESTAMPTZ、NULL可 | 取り下げ日時。NULLなら有効 |

Coreの `ProblemReference` は参照検査に必要な情報だけを表す。問題の本文などが追加されても、解説側へそのデータを渡す必要はない。

## 解説からの参照

`EditorialUnitOfWork` で問題を共有ロックし、同じトランザクション内で存在・削除状態・閲覧権限を検査する。公開問題は誰でも参照できる。非公開問題は `account_roles` のproblem-ownerまたはtesterを、本人・problemスコープ・問題UUIDを一致させて検査する。管理者・writer・別の問題の担当という理由だけでは許可しない。

存在しない・削除済み・閲覧できない場合は404。有効な通常大会に出題されている間は、その大会のcontest-setterも参照できる。大会の論理削除・出題の取り外し後には継承しない。バーチャル大会の運営担当には継承しない。

解説の外部キーが `problems.id` を参照する。移行時に孤立した既存解説がある場合は外部キー検証に失敗する。検証データの親を正しく登録するか、不要な検証データを整理してから移行する。存在しない問題を自動で補うことはしない。

## 取り下げ

問題の取り下げは `deleted_at` を設定する。DBトリガーが同じ問題の有効な解説にも削除日時を設定し、revisionを進める。問題と解説は一緒にcommit・rollbackされる。問題の物理削除は、解説からの外部キーがある間は許可しない。

解説側は親を先にロックし、その後に解説をロックする。問題削除と同時に解説を編集しても、逆順のロックによる競合や削除済み解説の復活を起こさない。

## ローカル確認用の登録

問題の作成APIはまだない。ローカルの検証用DBでは、次のSQLで公開問題を用意すると解説APIから参照できる。

```sql
INSERT INTO problems (id, visibility)
VALUES ('a8098c1a-f86e-4f70-917b-72f7c091480c', 'public');
```

通常大会の出題追加では `created_by_user_id` が本人と一致することを検査する。problem-ownerの付与だけでは作成者にならない。作成者不明の既存データを役割から推測して埋めない。

後から列を足す場合は新しいmigrationを追加し、適用済みmigrationは変更しない。
