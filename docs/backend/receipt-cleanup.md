# 期限切れの再送記録の削除

解説の作成要求と、大会の作成・参加要求の再送記録を定期的に削除する。保存期間は各機能のTTL設定で決まり、削除処理が動いていなくてもAPIは期限切れのキーを再利用できる。この処理は、期限切れの本文スナップショットなどをDBへ蓄積し続けないための保守処理である。

## 対象と期限

- `editorial_creation_receipts` と `contest_request_receipts` の、期限がDB時計のcutoff以前になった記録だけを削除する。期限ちょうどの記録も対象。
- 解説・大会・出題・役割・チーム・参加状態は削除しない。保存期間内の再送結果も維持する。
- 削除後のキーの再利用は、既存のTTL契約に従う。期限切れ後に同じ作成キーを使った場合、新しい作成要求として扱われ得る。

## 実行と設定

backendの起動時に1回、その後は設定間隔ごとに実行する。各回でテーブルごとに指定件数まで削除し、過去に逃した実行回数をまとめて取り戻す処理はしない。同じプロセス内では処理を重ねない。大量に期限切れの記録がある場合は複数回に分けて削除する。

| 環境変数 | 既定値 | 制約 |
| --- | --- | --- |
| `TRAOJUDGE_RECEIPT_CLEANUP_INTERVAL_SECONDS` | `600`（10分） | 正の32bit整数の秒数 |
| `TRAOJUDGE_RECEIPT_CLEANUP_BATCH_SIZE` | `1000` | 1〜10000。テーブルごとの上限 |

不正な設定は起動時に拒否する。削除に失敗した回は両テーブルの変更をrollbackしてログへ記録し、次の間隔で再試行する。HTTPの受付は継続する。ログには削除件数を残し、キー・本人ID・保存した本文などを出さない。

workerはHTTPサーバーと同じプロセス内で起動する。サーバーの終了・失敗・キャンセル時はworkerも中止する。外部スケジューラや公開HTTPエンドポイントは追加しない。

## 責務と競合

Coreの `ReceiptCleanupService` が `ReceiptCleanupUnitOfWork` を開始し、両テーブルへ同じcutoffと件数上限を渡してcommitする。InfraはSQLxトランザクションとSQL、bootstrapは設定・時刻のスケジューリング・実行結果のログを担当する。

削除対象を選ぶ際、記録行とその本人の行を `FOR UPDATE ... SKIP LOCKED` で確保する。APIのUoWが本人をロックしている間はその記録を次回へ回し、API開始時点では有効だった再送結果を処理途中で失わせない。保存期間を延長する更新中の記録も待たずに除外する。複数のbackendが同時に起動していても同じ記録を二重に処理しない。

期限の再検査と削除は同じトランザクションで行い、途中失敗では削除を確定しない。途中でworkerが中止された場合も、未確定のUoWを破棄してrollbackする。削除済み・期限延長済みの記録への再試行は追加の削除を起こさない。

## 検証

```sh
DATABASE_URL=postgresql://postgres:test@127.0.0.1:55432/postgres \
  cargo test -p traojudge-test --test receipt_cleanup -- --include-ignored
```

期限ちょうどの判定、有効な再送結果と本体の保持、件数の上限、並行worker、API処理中の利用者、記録の期限延長中、保存途中の失敗と次回の復旧を実DBで検査する。
