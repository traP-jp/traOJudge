# 問題登録・ジャッジ実行の受け渡し仕様

CLI・Back・Judgeが共有する登録データの必要情報と、未決の接続契約を記す。各分野の内部実装はここでは確定しない。用語の定義は[用語集](../../../domain/GLOSSARY.md)を参照する。

## CLIが送る情報

CLIが提供する問題登録データは、次の2つの組である。

| 区分 | 必要な情報 | 受け渡し |
| --- | --- | --- |
| メタデータ | ジャッジ手順を表すDAG、実行環境、ノード単位の結果をBackが解釈するための情報など | CLI専用APIへ登録する。具体的な外枠・フィールド構成はTODO |
| ファイル集合 | 全テストケース、テストコード、問題得点計算ロジックを含む、実行に必要なファイル一式 | CLI専用APIが発行する署名付きURLでS3へ直接アップロードし、APIへ完了通知する |

ファイル集合を登録する責務はCLIが担う。得点計算ロジックは作問者が提供する実行物であり、コンテストの得点集計・タイブレーク方式とは区別する。問題の得点はジャッジプログラムから報告され、コンテスト得点の集計はサービス側で行う。

## ジャッジ定義とジャッジ実行要求

再利用するジャッジ定義と、一回の実行を依頼するジャッジ実行要求を区別する。

| 段階 | 持つ情報 | 用途 |
| --- | --- | --- |
| ジャッジ定義 | DAG・実行環境などの問題定義と、作問ファイルへの参照。提出ごとのソース参照・言語はまだ具体化されていない | CLIによる問題登録。複数の提出から利用する定義 |
| ジャッジ実行要求 | 使用版を固定した問題定義に、提出コードのS3参照・提出言語などを追加した、実行ごとの情報 | BackとJudgeの間で一回のジャッジ実行を依頼するための表現 |

ジャッジ実行要求として実行内容を特定するため、少なくとも次の情報が必要である。フィールド名とシリアライズ形式は未決である。

| 情報 | 意味・決定状況 |
| --- | --- |
| 実行ID | Backが発行する、要求と結果を対応付けるID。再配信では同じID、再ジャッジでは別ID |
| 使用する問題定義 | 要求作成時に版を固定した問題・ジャッジ定義・作問ファイルの情報または参照 |
| 提出コードのS3参照 | 保管先・オブジェクトキー・必要な版情報を含むオブジェクト参照。Judgeの実行基盤の権限で取得する。フィールド名と版の識別方法はTODO |
| 提出言語 | UI・CLI・Back・Judgeで共有するサービス共通の言語ID。Backが受け付けたIDをそのままJudgeへ渡す。IDの一覧・具体的な表現はTODO |

ジャッジ実行要求には、固定したジャッジ定義と提出固有入力の組を含める。Backが提出コードのS3参照・提出言語などの入力を供給し、Judgeが入力を適用して実行手順を組み立てる。具体的なフィールド名とシリアライズ形式は未決である。参照実装の内部型と、本書の各用語をそのまま一対一には対応付けない。

| 分野 | 提出後の責務 |
| --- | --- |
| Back | 使用版を固定した定義と、実行ID・提出コードのS3参照・提出言語などを含む実行要求を作り、要求キューへ送る |
| Judge | 要求の定義と入力から実行手順を具体化し、必要ファイルを取得して実行する |

提出コードの取得には、Backが発行する署名付きダウンロードURLを使う方式ではなく、オブジェクト参照を渡す方式を採用する。Judgeの実行基盤が持つ権限でS3へアクセスする。利用者からのアップロードには、引き続きAPI発行の署名付きURLを使う。

## 結果の受け渡しと解釈

JudgeはDAGのノード単位で結果を返す。Backは、作問者がCLIから登録した結果解釈用の情報に基づき、その結果を解釈する。要求と結果は同じ実行IDで対応付ける。

結果解釈用の情報の形式と、ノードの識別方法・結果フィールドはTODOである。問題得点計算ロジックが報告する得点を使う方針は維持し、コンテストの得点集計・タイブレークはサービス側で行う。

参照実装の作問形式にはテキスト・スクリプトの内容をインラインで持つ部分があり、実行環境のコンテナイメージは構築例の実行時に別引数で指定される。今回の「メタデータ＋ファイル集合」との対応は未決である。これらを、そのまま今回の登録APIの確定フィールドとして扱わない。

参照実装には作問形式・登録済み形式・実行時形式がある。今回の提出後の具体化はJudgeの責務とする。問題登録時の正規化・登録形式への変換の担当は未決であり、参照リポジトリに実装が存在することだけで割り当てない。

既存Backは登録済み定義と入力値を渡し、Judge側で実行時形式を具体化している。ただし、既存の提出ソース入力はコード本文の文字列であり、今回要求するS3参照ではない。今回のジャッジ実行要求では、S3から対象コードを取得できるように入力契約を更新する必要がある。時間制限・メモリ制限なども既存実装にあるが、今回の受け渡しでの必須性・表現・供給責任はTODOとして扱う。

## 確定している周辺契約

- CLI専用APIは利用者に紐づく開発者トークンで認証する。
- APIが権限確認と署名付きURL発行を担い、CLIがS3へ直接転送してAPIへ完了通知する。
- Backはジャッジ要求の作成時に、使用する問題・ジャッジ定義・ファイルの版を固定する。
- ジャッジ実行要求には、ジャッジ定義に加えて提出コードのS3参照・提出言語が必要になる。
- Backは定義と提出固有入力の組を渡し、Judgeが実行手順を具体化する。
- 提出コードは保管先・オブジェクトキー・必要な版情報を渡し、Judgeの実行基盤の権限で取得する。
- 提出言語にはサービス共通の言語IDを使い、Backが受け付けたIDをそのままJudgeへ渡す。
- Backが実行IDを発行し、Judgeは結果に同じ実行IDを付ける。同じ要求の再配信は同じID、再ジャッジは別IDとする。
- Judgeはノード単位で結果を返し、Backが作問者の登録情報に基づいて解釈する。
- JudgeはDBを直接読み書きせず、SQSで要求・結果を受け渡し、必要ファイルをS3から取得する。結果のDB反映はBackが担う。

問題ごとの言語制約には禁止言語タグを使い、言語更新後も過去問題への提出を継続できる方式を目指す。タグの判定・管理はBackのTODOとして扱い、実行時入力へ渡す共通の言語IDと区別する。
