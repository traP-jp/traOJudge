# 問題登録・ジャッジ実行の受け渡し仕様

CLI・APIサーバー（Back）・インフラが共有する登録データの必要情報と、未決の接続契約を記す。DAGの解決・実行手順の具体化・実行順序の制御はAPIサーバー担当、実行環境周りはインフラ担当が実装する。以下の実行基盤は、インフラ担当が提供する環境と接続実装を指す。キューで依頼する処理はDAGの実行ノード1つずつとし、プロセス配置とメッセージ形式は未決である。用語の定義は[用語集](../../../domain/GLOSSARY.md)を参照する。

AWS側のAPIとインフラはまとめて設計する。この文書の担当分野は実装の窓口を表し、設計上の接続は[AWSの構成ブロック](../../../services/aws-building-blocks.md)で扱う。登録はCLI↔B2/B4、実行要求・結果はB2↔B5↔B6、実行環境の指定はB6↔B7へ対応付ける。

## CLIが送る情報

CLIが提供する問題登録データは、次の2つの組である。

| 区分 | 必要な情報 | 受け渡し |
| --- | --- | --- |
| メタデータ | ジャッジ手順を表すDAG、実行環境、ノード単位の結果をBackが解釈するための情報など | CLI専用APIへ登録する。具体的な外枠・フィールド構成はTODO |
| ファイル集合 | 全テストケース、テストコード、問題得点計算ロジックを含む、実行に必要なファイル一式 | CLI専用APIが発行する署名付きURLでS3へ直接アップロードし、APIへ完了通知する |

ファイル集合を登録する責務はCLIが担う。得点計算ロジックは作問者が提供する実行物であり、コンテストの得点集計・タイブレーク方式とは区別する。問題の得点はジャッジプログラムから報告され、コンテスト得点の集計はサービス側で行う。

## 登録完了の条件

CLIからの完了申告を受け、必要ファイル・メタデータ・参照の検証が通った時点で問題版を確定する。ジャッジの試行実行成功を登録完了の条件にはしない。具体的な検証項目・応答・競合更新はCONTRACT-02/05で具体化する。ユーザーとの操作の流れは[手元で作った問題のファイルを登録する](../../scenarios/problems/upload-problem-files.md)に記す。

## ジャッジ定義とジャッジ実行要求

ジャッジ定義の構造は機能要求の[DAG定義](../02-functions/judge-dag.md)を参照する。DAG定義の具体的なシリアライズ形式は実装で定める。

再利用するジャッジ定義と、一回の実行を依頼するジャッジ実行要求を区別する。

| 段階 | 持つ情報 | 用途 |
| --- | --- | --- |
| ジャッジ定義 | DAG・実行環境などの問題定義と、作問ファイルへの参照。提出ごとのソース参照・言語はまだ具体化されていない | CLIによる問題登録。複数の提出から利用する定義 |
| ジャッジ実行要求 | 使用版を固定した問題定義に、提出コードのS3参照・提出言語などを追加した、実行ごとの情報 | APIサーバーが一回のジャッジを制御するための情報。実行基盤には実行ノード1つずつノード実行要求を渡す。具体的なフィールド対応はTODO |

ジャッジ実行要求として実行内容を特定するため、少なくとも次の情報が必要である。フィールド名とシリアライズ形式は未決である。

| 情報 | 意味・決定状況 |
| --- | --- |
| 実行ID | Backが発行する、要求と結果を対応付けるID。再配信では同じID、再ジャッジでは別ID |
| 使用する問題定義 | 要求作成時に版を固定した問題・ジャッジ定義・作問ファイルの情報または参照 |
| 提出コードのS3参照 | 保管先・オブジェクトキー・必要な版情報を含むオブジェクト参照。Judgeの実行基盤の権限で取得する。フィールド名と版の識別方法はTODO |
| 提出言語 | UI・CLI・Back・Judgeで共有するサービス共通の言語ID。Backが受け付けたIDをそのままJudgeへ渡す。IDの一覧・具体的な表現はTODO |

ジャッジ実行要求には、固定したジャッジ定義と提出固有入力の組を含める。APIサーバーが入力を適用して実行手順を組み立て、DAGの依存関係を解決して実行順序を制御する。キューへは実行可能な実行ノードを1つずつ依頼する。要求・結果の具体的なフィールド名とシリアライズ形式、実行・ノード・試行の識別方法は未決である。参照実装の内部型と、本書の各用語をそのまま一対一には対応付けない。

| 分野 | 提出後の責務 |
| --- | --- |
| APIサーバー | 使用版を固定した定義と提出固有入力から実行手順を具体化する。DAGの依存関係・実行順序を制御し、実行基盤に処理を依頼して結果を解釈・反映する |
| インフラ | 実行環境とSQS・S3への接続を提供する。APIサーバーから指定された処理を実行できるようにし、結果を返す |

提出コードの取得には、Backが発行する署名付きダウンロードURLを使う方式ではなく、オブジェクト参照を渡す方式を採用する。Judgeの実行基盤が持つ権限でS3へアクセスする。利用者からのアップロードには、引き続きAPI発行の署名付きURLを使う。

## 結果の受け渡しと解釈

実行基盤はノード単位の処理結果を返す。APIサーバーは、作問者がCLIから登録した結果解釈用の情報に基づき、その結果を解釈し、DAGの依存関係に従って次の処理を制御する。要求と結果は同じ実行IDで対応付ける。ノードの試行を識別する方法はTODOである。

結果解釈用の情報の形式と、ノードの識別方法・結果フィールドはTODOである。問題得点計算ロジックが報告する得点を使う方針は維持し、コンテストの得点集計・タイブレークはサービス側で行う。

## ケース単位の進捗に必要な情報

ジャッジ中に完了したテストケース数を表示し、不正解や時間切れでも残りをすべて実行する。ノード完了とケースの判定完了を同一とはしない。[進捗表示の制約](../../submission-progress-constraints.md)に従い、ケースの識別、どの結果でケースの判定完了を認めるか、最終集計との区別を具体化する。

ケースの判定完了が既存のノード結果から分かる場合は、APIがその結果を解釈して進捗を作る。1ノード内の複数ケースの途中経過も必要なら、途中の事実を報告する方法かノード構成を検討する。実行を依頼する単位は、引き続きDAGの実行ノード1つずつとする。内部メッセージの形式はここでは確定しない。

ケースの不正解・時間切れを、全体の実行を中止する基盤障害とは区別して解釈できる情報も必要である。コンパイル不能や基盤障害で続けられない場合の終了・再試行は未決。CLIの登録情報と実行結果の対応をCONTRACT-07/08で詰める。

## 確定している周辺契約

- CLI専用APIは利用者に紐づく開発者トークンで認証する。
- APIが権限確認と署名付きURL発行を担い、CLIがS3へ直接転送してAPIへ完了通知する。
- Backはジャッジ要求の作成時に、使用する問題・ジャッジ定義・ファイルの版を固定する。
- ジャッジ実行要求には、ジャッジ定義に加えて提出コードのS3参照・提出言語が必要になる。
- APIサーバーが定義と提出固有入力から実行手順を具体化し、DAGの解決と実行順序の制御を担う。実行環境周りはインフラ担当が実装する。
- 提出コードは保管先・オブジェクトキー・必要な版情報を渡し、Judgeの実行基盤の権限で取得する。
- 提出言語にはサービス共通の言語IDを使い、Backが受け付けたIDをそのままJudgeへ渡す。
- Backが実行IDを発行し、Judgeは結果に同じ実行IDを付ける。同じ要求の再配信は同じID、再ジャッジは別IDとする。
- 実行基盤はノード単位で結果を返し、APIサーバーが作問者の登録情報に基づいて解釈し、次の処理を制御する。
- 実行基盤はDBを直接読み書きせず、SQSで要求・結果を受け渡し、必要ファイルをS3から取得する。結果のDB反映はAPIサーバーが担う。

問題ごとの言語制約には禁止言語タグを使い、言語更新後も過去問題への提出を継続できる方式を目指す。タグの判定・管理はBackのTODOとして扱い、実行時入力へ渡す共通の言語IDと区別する。
