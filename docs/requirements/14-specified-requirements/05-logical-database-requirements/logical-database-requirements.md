# 論理データベース要求

## ドメインモデル

DBは構造化データの保存を担い、PostgreSQL互換を優先する。提出ソース本体と作問ファイルはS3に保存する。既存DB設計は参照資料であり、今回の方針に合わせた見直しが必要である。

### エンティティ

以下を永続化の検討対象とする。テーブル分割を確定するものではない。

| データ群 | 主な対象 |
| --- | --- |
| 利用者・認証・権限 | 利用者、認証に必要な記録、セッション、ロールとスコープ |
| 問題・作問・解説 | 問題、テストケース、judge-definition、共同作業者、解説 |
| コンテスト | 通常・バーチャルコンテスト、問題の紐付け、参加、開催ルール、Clar |
| 提出・結果 | 提出の識別、ファイル参照、ジャッジ実行、判定・得点、再ジャッジ履歴 |
| ファイル管理 | 保存先を参照する情報、所有・利用関係、登録状態 |

### 属性

提出にはソース本体ではなく、ファイル保管先を参照する情報を持たせる設計とする。コンテストには得点計算のための方式とペナルティnが必要になる。

- TODO DATA-01: 各エンティティの属性、識別子、型、必須性、得点・時間の表現を定義する。
- TODO DATA-02: マジックリンク方式に必要な認証記録と、既存パスワード関連データの変更を定義する。

### 関係

利用者と対象問題・コンテストにはロールの関係がある。提出は利用者・問題・必要に応じてコンテストと関連し、ジャッジ実行と結果を持つ。ファイルの実体はDB外にあり、DB内の記録から参照する。

- TODO DATA-03: 多重度、参照整合性、ロールの関連付け、ファイル参照の持ち方を定義する。

### ライフサイクル

作問・公開・提出・ジャッジ・再ジャッジ・削除に伴うデータの変化を扱う。ロール定義にある論理削除と、それ以外の削除方式は区別して定義する必要がある。

- TODO DATA-04: 保存期間、論理／物理削除、退会後の記録、不要ファイルの削除を定義する。
- TODO DATA-05: 再ジャッジ中・完了後の現在結果と履歴の関係を確定する。

- 提出ソース本体をDBに保存しない。
- 基盤を後から差し替えられる構成とする。
