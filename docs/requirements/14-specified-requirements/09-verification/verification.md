## 機能要求の確認対象

| 要求 | 確認する内容 |
| --- | --- |
| REQ-PUBLIC-01・REGISTER-01 | 公開情報の閲覧、承認不要の登録、登録完了時のstandard-user付与と本人のセッション作成 |
| REQ-ROLE-01 | ロール定義と各操作の権限の対応 |
| REQ-AUTH-01 | 共通のマジックリンクによるメール認証、パスワードを要求しないこと、本人確認トークンの発行から30分の有効期限と一回限りの消費、確認後に発行する登録用トークンが期限を延長しないこと |
| REQ-AUTH-02 | APIの受付応答・メールで登録の有無を開示せず、メール確認後にだけ登録済みならログイン、未登録なら表示名の入力へ分岐すること。不正・期限切れ・使用済みトークンで登録の有無を開示しないこと |
| REQ-SESSION-01 | 最終アクセスから90日のセッションとCookieの有効期限、アクセスごとの延長、継続利用中に固定期限でログアウトしないこと、期限切れ・ログアウト・失効後は延長しないこと |
| REQ-SESSION-02 | ログアウト後に現在のセッションが失効してCookieが削除され、ほかの端末や別のブラウザのセッション、開発者トークン、役割は維持されること |
| REQ-SESSION-03 | メール変更完了の204応答で現在のセッションと同じCookieを共有するタブのログイン状態が維持され、セッションとCookieの期限が90日後まで更新されること。それ以外の本人の既存のセッションでは認証必須APIへのアクセスが401となり、期限延長で復活しないこと。維持するセッションは完了要求のCookieで特定し、変更不成立を理由に既存のセッションを失効しないこと |
| REQ-CONTENT-01・CONTEST-01 | 作問・解説、通常／virtualコンテスト、Clarの対象範囲 |
| REQ-CLI-01〜05 | CLI専用APIを通じた問題登録、名前付きトークンの発行・認証・失効、任意の有効期限（省略時は無期限）、秘密の文字列を発行時だけ表示すること。失効後の新しい要求は401となり、受け付け済み登録は専用の継続トークンで期限まで状態確認・完了できること。署名付きURLでの直接アップロードと完了通知。DAG・実行環境・ノード結果の解釈情報のメタデータと全テストケース・テストコード・問題得点計算ロジックの受け渡し |
| REQ-JUDGE-01〜04 | 要求・結果の実行IDの対応と再配信・再ジャッジ時の識別。実行基盤がDBへ直接接続せず、APIサーバーが結果をDBへ反映すること。要求後の問題更新が使用版を変えないこと |
| REQ-JUDGE-05 | 同じ実行IDの同じ結果を再受信しても、得点や結果が二重計上されないこと |
| REQ-JUDGE-06 | ジャッジ定義とジャッジ実行要求を区別し、各実行に対応する提出コードのS3参照・提出言語を受け渡せること |
| REQ-JUDGE-07 | APIサーバーがDAGの依存関係を解決し、実行ノード1つずつ依頼できること。前段の結果に基づく後続実行を、実行環境と接続して確認すること |
| REQ-JUDGE-08 | オブジェクト参照で指定された提出コードを、Judgeの実行基盤の権限で取得できること |
| REQ-JUDGE-09 | Judgeからノード単位の結果が返り、作問者がCLIから登録した情報に基づいてBackが解釈できること |
| REQ-LANG-01 | UI・CLI・Back・Judgeで言語IDが共通であり、受け付けたIDがそのまま実行時入力としてJudgeへ渡ること |
| REQ-LANG-02 | 問題ごとの禁止言語タグと、言語更新後の過去問題への提出継続。具体的な判定条件はBackのTODOに従う |
| REQ-FILE-01〜02 | S3への保存とWebUIからの直接アップロード、Backによる提出確定・ジャッジ依頼、提出ソース本体をDBに保存しないこと |
| REQ-SCORE-01〜04 | 最高得点の集計、両タイブレーク方式、nの変更条件、ペナルティ対象と除外判定 |
| REQ-MAIL-01 | キューへの送信要求、利用者による再送要求、専用の配送失敗処理・自動再試行を設けないこと |
