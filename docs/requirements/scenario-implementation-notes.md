# シナリオを実装するときの対応メモ

[日常語で書いたシナリオの一覧](mutation-scenarios.md)に対応する、入力・識別子・状態変化・単独確認のメモを残す。各シナリオ本文は利用者の行動と結果を扱い、APIや保存処理などの実装上の表現はこちらで扱う。シナリオの番号は一覧の番号と対応する。

以下は元の棚卸しから引き継いだ初版であり、未決事項を合意済みとして扱わない。

## A5〜A8：外部サービスを使う認証

登録・ログイン・既存利用者への認証手段の追加・解除を、それぞれ独立したシナリオとして扱う。Google・GitHub・traQは既存OpenAPI/UIに存在する候補であり、全てのリリース採用を決めたものではない。採用範囲はAUTH-01/DEP-01と合わせて決める。

| シナリオ | 成立する事実 | 確認する分岐 |
| --- | --- | --- |
| A5 外部アカウントで登録 | 利用者登録、外部identityの対応付け、standard-user付与 | 本人確認の中断・失敗、登録済みidentity、追加情報の不足 |
| A6 外部アカウントでログイン | 対応する既存利用者のログイン成立 | 未連携identity、失効・不正な認証結果、外部サービスの障害 |
| A7 認証手段の追加 | 現在の利用者に認証手段が追加された | 他利用者との対応付け済み、同じ利用者への追加済み、途中のログイン状態の変化 |
| A8 認証手段の解除 | 対象の認証手段が利用者から解除された | 本人の手段ではない、最後のWebログイン手段、同時に複数手段を解除する場合 |

外部identityはproviderとprovider内の安定した識別子で区別する。連絡先メールアドレスの一致だけで、別の利用者への連携やアカウント統合を行わない。CLI用開発者トークンは、最後のWebログイン手段を保護する判定には数えない。

既存の[UIの作問ガード](../../UI/src/composables/useTraqAuthGuard.ts)にはtraQ認証の有無で作問可否を判定する箇所がある。今回のシナリオでは認証手段の追加とロール付与を別操作としているため、その対応は権限設計時に整理する。traQのneoShowcase側入口とAWS側APIの連携方法も未決である。

単独確認では外部サービスの本人確認結果をfakeで与え、登録・ログイン・連携追加・解除の成功と上記の失敗分岐を確認する。認証結果の受け取り方、対応付けに必要な入力と識別子、セッションの扱いはOpenAPIと保存設計で具体化する。

## P2：CLIで問題版を登録する

開始条件は、問題IDがあり、CLIが利用者に紐付くトークンで認証でき、その利用者が問題を更新できること。

| 順序 | 誰が何をするか | 入力 | 成立する事実・ユーザーへの結果 |
| --- | --- | --- | --- |
| 1 | 作問者がCLIから更新登録を開始する | 問題ID、メタデータ、ファイル一覧、実行環境の指定 | 更新登録が開始された。登録IDと転送条件を返す |
| 2 | CLIが指定先へファイルを直接転送する | 転送条件と必要ファイル | 転送成功／失敗をCLIが把握する。この段階では問題版は未確定 |
| 3 | CLIがAPIへ完了を申告する | 登録ID | APIが必要ファイル・メタデータ・参照を検証する |
| 4 | APIが検証済みの内容を採用する | 検証結果と固定したファイル参照 | 問題版が確定した。問題ID・版を返し、このシナリオを完了する |

登録完了は、必要ファイル・メタデータ・参照の検証が通った時点とする。ジャッジの試行実行成功を登録完了の条件にはしない。これはユーザー確認済みの方針である。公開範囲はR2で変更する。

失敗分岐は、認証・権限不足、転送失敗、ファイル不足、メタデータ不正、参照不整合。検証を通過しない登録から新しい採用版を作らない。編集中に権限が失われた場合の完了可否、競合更新、完了申告の再送は決定表で詰める。

単独実装では、利用者・問題権限・ファイル確認のfixture/fakeを使う。完了条件は、正常な一式から版が確定し、不足・不整合のある一式では確定しないこと。具体的な外枠・検証項目は[受け渡し仕様](14-specified-requirements/01-external-interfaces/problem-registration-contract.md)へ記録する。

## S1：コードを提出して判定結果が確定する

開始条件は、利用者が認証済みで、問題の採用版と対応言語があり、その文脈で提出できること。コンテスト提出では、参加状態と開催条件も受け取る。

| 順序 | 誰が何をするか | 入力 | 成立する事実・ユーザーへの結果 |
| --- | --- | --- | --- |
| 1 | 利用者がUIから転送先を要求する | 問題ID、提出言語、ファイル条件、必要ならコンテストの文脈 | アップロード先と転送に必要な情報を返す |
| 2 | UIが提出ソースを直接転送する | 転送条件とソース | 転送成功／失敗をUIが把握する。この段階では提出は未確定 |
| 3 | 利用者がUIから提出を確定する | 転送済みソースの識別、問題・言語・提出文脈 | 認証・権限・ソース・言語を確認し、提出が受理された。採用版と実行IDを固定して提出ID・実行IDを返す |
| 4 | ジャッジ受付後、処理が進む | 固定済みの提出と採用版 | 判定待ち・実行中の状態が成立する。クラスタ内部の通信は別途設計する |
| 5 | 最終結果が得られ、APIが反映する | 実行IDに対応する最終結果 | 判定が確定した。得点・判定と対象の提出／実行を識別できる |
| 6 | コンテスト提出ならサービスが得点を反映する | 確定した判定、コンテスト・参加者・採点ルール | コンテスト得点・順位への反映が成立する。通常提出ではこの段階を通らない |

提出の受付成功と判定確定は別の時点である。ユーザーが結果を受け取る方法は、後で読み取り／通知の契約として決める。

失敗分岐は、未認証、権限不足、ファイル不足、禁止／非対応言語、提出期間外。受理後には基盤上の失敗もあり得る。誤答などの判定結果と、APIが提出自体を拒否することを区別する。

単独実装では、認証・権限・問題版・転送済みファイルと最終判定をfixture/fakeで与える。完了条件は、受付時に提出と使用版・実行IDが固定され、対応する結果だけが反映され、同じ結果の再受信で得点を二重反映しないこと。クラスタ内部の実装完成をこの確認の前提にしない。

## 独立に実装するための切り口

| 切り出す作業 | 共通の接続点 | 単独で確認する終点 |
| --- | --- | --- |
| A1/A2/A5/A6の認証操作 | 認証された利用者の識別、未認証・失効の結果 | メール・外部認証それぞれで登録・ログインでき、共通のログアウトが成立する |
| A3/A4/A7/A8の認証手段の管理 | 現在の利用者と、Web/CLIそれぞれの認証手段 | メール変更・CLIトークン管理・外部認証手段の追加／解除を本人が行える |
| R1/R2/R3の権限・アクセス制御 | 利用者・対象・操作に対する許可／拒否 | 付与／剥奪と公開範囲・参加状態に応じて操作可否が変わる |
| P1/P2の問題登録 | メタデータ、ファイル集合、登録ID、確定した問題版 | CLI操作から検証済みの問題版を作れる |
| S1/S2の提出操作 | 問題版・言語・ソース参照、提出／実行ID、最終判定 | UI操作から提出を受理し、対応する判定を反映できる |
| C1/C2/C3のコンテスト操作 | コンテスト・問題・参加者・採点設定・Clar | 作成・設定・問題構成変更・質問／回答が成立する |
| O1/O2の解説・プロフィール操作 | 利用者・対象・更新内容、R1/R2の権限 | 投稿・更新・削除が権限に従って成立する |

これは実装の切り口であり、別サービスへの配置や担当人数の追加を要求しない。各作業はAPIの状態変化と、対応するUI/CLI操作を一緒に確認する。共有契約は1か所で定義し、利用側は同じ例をfakeに使う。

fixtureの例は「認証済みのwriter」「ある問題を更新可能な利用者」「投稿済みの公開問題版」「開催中で参加済みのコンテスト」。実装者ごとに権限や識別子の意味を作り直さない。

## 作業票の形式と未決事項

各シナリオの作業票には、主担当・編集範囲、開始条件の具体例、コマンドの必須入力、状態変化とイベント、受付／完了時の結果、失敗分岐、再送時の扱い、単独確認例を記載する。受付・完了・中止のどこまでを1作業とするか明示する。

| 未決事項 | 影響するシナリオ | 決めること |
| --- | --- | --- |
| MUT-01 認証操作の契約 | A1/A2/A3/A5/A6 | リンクの期限・一度だけの消費、登録時のセッション、メール・外部認証それぞれの登録／ログインとの関係 |
| MUT-02 初期権限と権限変更中の操作 | R1/P1/C1/P2/S1 | 問題・コンテスト作成者へのロール、付与／剥奪できる主体、操作途中の権限失効をいつ検査するか |
| MUT-03 更新登録の詳細 | P2/P3 | メタデータ外枠・ファイル／参照検証の具体項目、競合更新、更新失敗後の状態。完了条件は検証通過として確定済み |
| MUT-04 コマンドの再送 | 各mutation | 同じ操作の再送を識別する情報、同じ結果を返す条件、新しい操作として扱う条件 |
| MUT-05 再ジャッジの採用結果 | S2/S3 | 実行中の表示対象、古い結果の遅着、要求時に採用する問題版、一括処理の対象確定と一部失敗 |
| MUT-06 コンテストの状態 | R3/C1/C2/C3/S1 | 参加・提出・設定変更が可能な期間、virtualの開始条件、Clarの公開範囲 |
| MUT-07 公開範囲と利用可否 | R2/P1/P2/O1 | 公開可能な条件、非公開化・削除後の既存参加者や提出への影響 |
| MUT-08 外部認証の採用・連携 | A5/A6/A7/A8 | 対応provider、メールアドレスを持たない利用者の登録、同一providerの複数アカウント、解除時のセッション、最後のログイン手段の保護、traQ認証と権限の対応 |

現時点は全体の時系列と実装シナリオの初版である。P2・S1は詳細化したが、具体的な入力例・未決事項・主担当が揃うまでは実装着手条件を満たしたとは扱わない。
