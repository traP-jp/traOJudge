# シナリオを実装するときの対応メモ

[日常語で書いたシナリオの一覧](mutation-scenarios.md)に対応する、入力・識別子・状態変化・単独確認のメモを残す。各シナリオ本文は利用者の行動と結果を扱い、APIや保存処理などの実装上の表現はこちらで扱う。シナリオの番号は一覧の番号と対応する。

以下は元の棚卸しから引き継いだ初版であり、未決事項を合意済みとして扱わない。

## A5〜A8：外部サービスを使う認証

登録・ログイン・既存利用者への認証手段の追加・解除を、それぞれ独立したシナリオとして扱う。外部認証先はtraQ・Google・GitHubの3つとする。認証責任の配置はAUTH-01/DEP-01と合わせて決める。

| シナリオ | 成立する事実 | 確認する分岐 |
| --- | --- | --- |
| A5 外部アカウントで登録 | 利用者登録、外部identityの対応付け、standard-user付与 | 本人確認の中断・失敗、登録済みidentity |
| A6 外部アカウントでログイン | 対応する既存利用者のログイン成立 | 未連携identity、失効・不正な認証結果、外部サービスの障害 |
| A7 認証手段の追加 | 現在の利用者に認証手段が追加された | 他利用者との対応付け済み、同じ利用者への追加済み、途中のログイン状態の変化 |
| A8 認証手段の解除 | 対象の認証手段が利用者から解除された | 本人の手段ではない、最後のWebログイン手段、同時に複数手段を解除する場合 |

外部identityはproviderとprovider内の安定した識別子で区別する。外部サービスからメールアドレスを取得できなくても登録できる。連絡先メールアドレスの一致だけで、別の利用者への連携やアカウント統合を行わない。CLI用開発者トークンは、最後のWebログイン手段を保護する判定には数えない。

既存の[UIの作問ガード](../../UI/src/composables/useTraqAuthGuard.ts)にはtraQ認証の有無で作問可否を判定する箇所がある。今回のシナリオでは認証手段の追加とロール付与を別操作としているため、その対応は権限設計時に整理する。traQのneoShowcase側入口とAWS側APIの連携方法も未決である。

単独確認では外部サービスの本人確認結果をfakeで与え、登録・ログイン・連携追加・解除の成功と上記の失敗分岐を確認する。認証結果の受け取り方、対応付けに必要な入力と識別子、セッションの扱いはOpenAPIと保存設計で具体化する。

## R1〜R4：操作ごとの許可と権限変更

[操作ごとの許可条件](permission-operations.md)を、認可判定と作業票の共通の入力にする。R1は役割ごとの付与・剥奪20シナリオ、R2は問題・解説それぞれの公開・非公開4シナリオ、R3は公開された通常大会への本人の参加、R4はバーチャル大会への本人の参加である。

権限変更の入力は、操作する利用者、対象の利用者、役割、必要なら問題ID・通常大会ID・バーチャル大会ID・解説ID。サービス全体の役割と、特定対象に限る役割を混同しない。成功時の事実は、指定した対象者の指定した範囲で役割が付いた・外れたこと。具体的なイベントの型名とHTTP契約は別途決める。

`contest-admin(C)` はCの `contest-setter` を付与できるが剥奪できない。`problem-owner(P)` はPの `tester` を付与できるが、剥奪の許可はない。どちらも剥奪は `service-admin` が行う。`service-admin` に業務操作すべてを許可する判定は作らない。

再送、同時変更、複数の役割から同じ許可を得る場合、操作途中の剥奪は未決。個別のシナリオがどの役割を変えたかを記録し、指定していない別の役割まで削除したり、許可がすべてなくなったと一律に案内したりしない。

単独確認は一覧末尾の例を使い、許可される主体、同じ役割でも対象が違う主体、追加できても剥奪できない主体を区別する。公開範囲やバーチャル大会への自己参加など、許可する主体が未決の操作は、成功する契約を確定する前に合意する。

## P2：CLIで問題版を登録する

開始条件は、問題IDがあり、CLIが利用者に紐付くトークンで認証でき、その利用者が登録内容に含まれる変更をすべて行えること。問題更新の許可だけでは、judge-definitionの追加・削除まで許可しない。差分ごとに問題・judge-definition・テストそれぞれの操作へ対応付けて確認する。テストの操作権限は未決。

| 順序 | 誰が何をするか | 入力 | 成立する事実・ユーザーへの結果 |
| --- | --- | --- | --- |
| 1 | 作問者がCLIから更新登録を開始する | 問題ID、メタデータ、ファイル一覧、実行環境の指定 | 更新登録が開始された。登録IDと転送条件を返す |
| 2 | CLIが指定先へファイルを直接転送する | 転送条件と必要ファイル | 転送成功／失敗をCLIが把握する。この段階では問題版は未確定 |
| 3 | CLIがAPIへ完了を申告する | 登録ID | APIが必要ファイル・メタデータ・参照を検証する |
| 4 | APIが検証済みの内容を採用する | 検証結果と固定したファイル参照 | 問題版が確定した。問題ID・版を返し、このシナリオを完了する |

登録完了は、必要ファイル・メタデータ・参照の検証が通った時点とする。ジャッジの試行実行成功を登録完了の条件にはしない。これはユーザー確認済みの方針である。公開範囲はR2で変更する。

失敗分岐は、認証・権限不足、転送失敗、ファイル不足、メタデータ不正、参照不整合。検証を通過しない登録から新しい採用版を作らない。編集中に権限が失われた場合の完了可否、競合更新、完了申告の再送は決定表で詰める。

単独実装では、利用者・問題権限・ファイル確認のfixture/fakeを使う。完了条件は、正常な一式から版が確定し、不足・不整合のある一式では確定しないこと。具体的な外枠・検証項目は[受け渡し仕様](14-specified-requirements/01-external-interfaces/problem-registration-contract.md)へ記録する。

## S1：コードを提出して判定結果が確定する

開始条件は、利用者が認証済みで、問題の採用版と対応言語があり、その文脈で提出できること。コンテスト提出では、参加状態と開催条件も受け取る。

| 順序 | 誰が何をするか | 入力 | 成立する事実・ユーザーへの結果 |
| --- | --- | --- | --- |
| 1 | 利用者がUIから転送先を要求する | 問題ID、提出言語、ファイル条件、必要ならコンテストの文脈 | アップロード先と転送に必要な情報を返す |
| 2 | UIが提出ソースを直接転送する | 転送条件とソース | 転送成功／失敗をUIが把握する。この段階では提出は未確定 |
| 3 | 利用者がUIから提出を確定する | 転送済みソースの識別、問題・言語・提出文脈 | 認証・権限・ソース・言語を確認し、提出が受理された。採用版と実行IDを固定して提出ID・実行IDを返す |
| 4 | ジャッジ受付後、処理が進む | 固定済みの提出と採用版 | 判定待ち・実行中の状態が成立する。クラスタ内部の通信は別途設計する |
| 5 | 最終結果が得られ、APIが反映する | 実行IDに対応する最終結果 | 判定が確定した。得点・判定と対象の提出／実行を識別できる |
| 6 | コンテスト提出ならサービスが得点を反映する | 確定した判定、コンテスト・参加者・採点ルール | コンテスト得点・順位への反映が成立する。通常提出ではこの段階を通らない |

提出の受付成功と判定確定は別の時点である。ジャッジ中には完了したテストケース数を表示し、不正解・時間切れでも残りをすべて実行する。ケース完了数の観測・保存と閲覧に必要な条件は、読み取りAPI全体の設計に先立ってS4で具体化する。HTTPの経路や通知の形式は後で決める。

失敗分岐は、未認証、権限不足、ファイル不足、禁止／非対応言語、提出期間外。受理後には基盤上の失敗もあり得る。誤答などの判定結果と、APIが提出自体を拒否することを区別する。

単独実装では、認証・権限・問題版・転送済みファイルと最終判定をfixture/fakeで与える。完了条件は、受付時に提出と使用版・実行IDが固定され、対応する結果だけが反映され、同じ結果の再受信で得点を二重反映しないこと。クラスタ内部の実装完成をこの確認の前提にしない。

## S4：完了したケース数を見ながら待つ

[利用者のシナリオ](scenarios/submissions/watch-judging.md)と[基盤への制約](submission-progress-constraints.md)を対応付ける。確定した要望は、ジャッジ中に完了したテストケース数を表示すること、不正解や時間切れでも残りをすべて実行すること。

表示に最低限必要なのは、提出と対象の実行の識別、今回完了したケース数、確定済みかどうか。状態の詳しい区分、総数、更新の新旧や鮮度を区別する情報、ケース単位の公開項目は、表示・再接続の要求と合わせて決める。これは必要な意味の整理であり、OpenAPIのフィールド名ではない。

B2は、CLIが登録する解釈情報とノード結果からケースの判定完了を決める。ノード数をそのまま完了ケース数としない。B5/B6には、全体の終了前にその判断に必要な事実を届けられることが求められる。1ノード内で複数ケースを実行する場合も含めて、報告の粒度を確認する。

単独確認は、3ケースがT2→T1→T3の順に終わる例を使う。T1を不正解にしてもT3が実行され、完了数は1→2→3となる。重複結果、古い進捗の遅着、閲覧用接続の断と再取得、別の再採点からの結果も与える。一括再採点の「完了した提出数」と、個々の提出の「完了したケース数」は別の集計にする。

表示用接続の切断で採点を止めないこと、保存済みの状態から表示を再開することは設計案として整理した。更新遅延、全通知の描画を求めるか、公開範囲、コンパイル不能・基盤障害時の終了と復旧をMUT-10で詰める。内部通信の形式はまだ固定しない。

## 独立に実装するための切り口

| 切り出す作業 | 共通の接続点 | 単独で確認する終点 |
| --- | --- | --- |
| A1/A2/A5/A6の認証操作 | 認証された利用者の識別、未認証・失効の結果 | メール・外部認証それぞれで登録・ログインでき、共通のログアウトが成立する |
| A3/A4/A7/A8の認証手段の管理 | 現在の利用者と、Web/CLIそれぞれの認証手段 | メール変更・CLIトークン管理・外部認証手段の追加／解除を本人が行える |
| R1/R2/R3/R4の権限・アクセス制御 | 利用者・対象・操作に対する許可／拒否 | 付与／剥奪と公開範囲・参加状態に応じて操作可否が変わる |
| P1/P2の問題登録 | メタデータ、ファイル集合、登録ID、確定した問題版 | CLI操作から検証済みの問題版を作れる |
| S1/S2の提出操作 | 問題版・言語・ソース参照、提出／実行ID、最終判定 | UI操作から提出を受理し、全ケースを実行して対応する判定を反映できる |
| S4の途中表示 | 実行・ケースの識別、判定完了の事実、進捗、閲覧範囲 | 最終結果を待たずに完了数を表示し、重複・遅着・再接続・再採点を区別できる |
| C1/C2/C3のコンテスト操作 | コンテスト・問題・参加者・採点設定・Clar | 作成・設定・問題構成変更・質問／回答が成立する |
| O1/O2の解説・プロフィール操作 | 利用者・対象・更新内容、R1/R2の権限 | 投稿・更新が権限に従って成立する。解説の削除は許可する人の合意後に扱う |

これは実装の切り口であり、別サービスへの配置や担当人数の追加を要求しない。各作業はAPIの状態変化と、対応するUI/CLI操作を一緒に確認する。共有契約は1か所で定義し、利用側は同じ例をfakeに使う。

fixtureの例は「認証済みのwriter」「ある問題を更新可能な利用者」「投稿済みの公開問題版」「開催中で参加済みのコンテスト」。実装者ごとに権限や識別子の意味を作り直さない。

## 他のシナリオにも足していく細かさ

操作と結果だけでなく、その間に利用者が見たいことと、途中で離れた場合の扱いを記す。通信方式やDB構造を先に決めず、下表の問いから必要な制約を導く。

| 足す観点 | シナリオに書くこと | 実装へ渡す条件の例 |
| --- | --- | --- |
| 受付と完了の違い | 何を確認したら、受け付けた・終わったと伝えるか | 非同期に残る処理、保存が必要な状態 |
| 待っている間 | 何を、どの単位で、どの程度の遅れで見せるか | 観測する事実、更新頻度、同時に見る人の数 |
| 並列・順序・重複 | 複数の処理が違う順で終わる場合、何を数えるか | 識別、重複排除、古い更新を判別する情報 |
| 失敗と実行の継続 | 一部の失敗で全体を止めるか、誰に何を伝えるか | 結果と障害の分類、続行・再試行・終了の条件 |
| 離脱と復帰 | 画面を閉じる・通信が切れる・開き直すとどうなるか | 状態の保存、再取得、処理と接続の寿命 |
| 公開範囲と権限変更 | 途中の何を誰に見せ、権限変更後にどうするか | 閲覧時の認可、公開する項目、表示の更新 |
| 大量処理と混雑 | 一度に多数を頼むとき、通常の操作とどう共存するか | 容量、待ち時間、集計の単位、通知の集中 |

次の候補はP2のファイル転送・検証待ち、A1/A5の本人確認待ち、C3の質問への回答待ち、コンテストの得点・順位反映待ち。ここではそれらの表示や通知を新しい要件として確定しない。S4を最初の具体例として同じ観点で掘り下げる。

## 作業票の形式と未決事項

各シナリオの作業票には、主担当・編集範囲、開始条件の具体例、コマンドの必須入力、状態変化とイベント、受付／完了時の結果、失敗分岐、再送時の扱い、単独確認例を記載する。受付・完了・中止のどこまでを1作業とするか明示する。

| 未決事項 | 影響するシナリオ | 決めること |
| --- | --- | --- |
| MUT-01 認証操作の契約 | A1/A2/A3/A5/A6 | リンクの期限・一度だけの消費、登録時のセッション、メール・外部認証それぞれの登録／ログインとの関係 |
| MUT-02 初期権限と権限変更中の操作 | R1/P1/C1/P2/S1/O1 | 問題・大会・解説の作成者への役割、複数役割の評価、自己付与、最後の担当の剥奪、途中の権限失効の検査時点。明記済みの付与／剥奪主体は個別シナリオに従う |
| MUT-03 更新登録の詳細 | P2/P3 | メタデータ外枠・ファイル／参照検証の具体項目、競合更新、更新失敗後の状態。完了条件は検証通過として確定済み |
| MUT-04 コマンドの再送 | 各mutation | 同じ操作の再送を識別する情報、同じ結果を返す条件、新しい操作として扱う条件 |
| MUT-05 再ジャッジの採用結果 | S2/S3 | 実行中の表示対象、古い結果の遅着、要求時に採用する問題版、一括処理の対象確定と一部失敗 |
| MUT-06 コンテストの状態 | R3/R4/C1/C2/C3/S1 | 参加・提出・設定変更が可能な期間、virtualの開始条件、Clarの公開範囲 |
| MUT-07 公開範囲と利用可否 | R2/P1/P2/O1 | 公開・非公開の変更を許す人（service-admin の問題非公開化以外）、公開可能な条件、非公開化・削除後の既存参加者や提出への影響 |
| MUT-08 外部認証の採用・連携 | A5/A6/A7/A8 | 対応provider、メールアドレスを持たない利用者の登録、同一providerの複数アカウント、解除時のセッション、最後のログイン手段の保護、traQ認証と権限の対応 |
| MUT-09 ロール定義に明示のない操作 | P3/S1/S3/C1/C2/R1/R4/O1 | テスト操作、非公開問題への試し提出、問題単位・バーチャル大会の一括再採点、バーチャル大会の削除・問題取り外し・自己参加、サービス管理者の任命・解任、解説削除。「自身の問題」の判定と大会の設定項目別の許可 |
| MUT-10 提出の途中表示 | S1/S2/S3/S4 | 完了数の表示と不正解・時間切れで全ケースを継続することは確定。ケース完了の解釈、総数・詳細の公開範囲、更新遅延と負荷、全通知の描画、保存・再取得、コンパイル不能・基盤障害時の扱いを具体化する |

現時点は全体の時系列と実装シナリオの初版である。P2・S1は詳細化したが、具体的な入力例・未決事項・主担当が揃うまでは実装着手条件を満たしたとは扱わない。
