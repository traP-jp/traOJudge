# 提出の進捗表示から、API・実行基盤に必要な条件を整理する

[結果を待つ人のシナリオ](scenarios/submissions/watch-judging.md)をもとに、利用者に見せたい動きと、実装側に必要になる条件を対応付ける。確定した要望は完了ケース数の途中表示と、不正解・時間切れでも全ケースを継続すること。表示範囲・遅延目標・通信形式は未決。

ユーザーからの要望は、提出結果を待つ間にも「テストケース1/n」のように進み具合を都度表示すること。確認済みの意味は「判定が完了したケース数」であり、実行中のケースの番号ではない。総数の併記やケースごとの判定表示は、この要望から必須とはしない。

## 最初に分けること

| 論点 | この案での扱い | 確定しないこと |
| --- | --- | --- |
| 利用者に見せたいこと | 最終結果の前にも進み具合が分かる | 各ケースの判定・名前・内容の公開範囲 |
| 進捗の単位 | ケースの判定完了を数える | DAGのノード数と同一とすること |
| 実行を依頼する単位 | 既存の決定どおり、DAGの実行ノード1つずつ | 1ケースを必ず1ノードに分割すること |
| 内部の通信 | 途中経過を必要な時点でAPIへ渡せることを条件にする | メッセージ形式・配送方式・キュー構成 |
| 利用者への更新 | 許可された進捗を再取得・更新できること | HTTPの経路、接続の維持方法、通知手段 |

[DAGの制御はAPIサーバー、実行環境はインフラ](../services/aws-building-blocks.md)という分担を維持する。進捗を表示するために、ワーカーへDAG全体の制御を移さない。読み取りAPIの全体設計を待つ必要はないが、このシナリオに必要な観測・保存・閲覧の条件は先に決める。

## 表示の要望と、基盤への影響

| 利用者に見せたいこと | 必要な情報・振る舞い | 影響するブロック |
| --- | --- | --- |
| 受け付けたあと、待っていると分かる | 受付を保存し、提出と今回の実行を識別する。実行開始を観測するまでは、要求の送信を「実行開始」と扱わない | B2 API、B3 保存 |
| 実際に採点が始まったと分かる | 何を開始と呼ぶかを決め、開始した事実をAPIが受け取れる。開始通知を使うなら実行基盤にも報告が必要 | B2、B5 通信、B6 ワーカー |
| ケースの判定が終わるたびに進む | 最終集計より前に、どのケースが完了したかをAPIが解釈できる。ノード内に複数ケースをまとめるなら、最後のノード終了報告だけで足りるかを確認する | CLIの定義、B2、B5、B6 |
| 完了した件数が分かる | 今回の採用版に対するケースの識別と、判定完了の条件を定義する。総数も表示するなら、その実行の対象数を得て、問題更新で分母を変えない | CLIの定義、B2、B3 |
| 並列実行でも正しい件数が出る | 実行順やノード番号ではなく、完了したケースの集合を集計する | B2、B3 |
| 重複や遅着で表示が壊れない | 実行・ノード・試行・ケースを対応付け、どの試行の結果を採用するかを決める。画面への更新にも新旧を区別する情報が必要 | B2、B3、B5、WebUI |
| ページを開き直しても追い付ける | 今の状態を再取得できる。過去に流れた通知を受け取っていない人でも復元できる。API再起動後も復元できる | B2、B3、WebUI |
| 別のAPIプロセスにつながっても同じ進捗が見える | 結果を受け取ったプロセス以外からも、保存済みの状態を取得・配信できる。接続中のプロセスのメモリーだけに置かない | B1 入口、B2、B3 |
| 通信が切れても採点は続く | 閲覧用接続の寿命と採点の寿命を分ける。再接続時に最新状態を取得する | WebUI、B1、B2、B3 |
| 不正解・時間切れでも残りが実行される | ケースの判定を、残りの実行を止める異常終了と区別する。B2は全ケースを進め、B6は判定に必要な事実を返す | B2、B5、B6 |
| 全件完了後、確定結果を見られる | ケース完了、最終判定・得点の確定、大会順位への反映を別の事実にする | B2、B3 |
| ケースの不正解と、採点を続けられない障害を区別できる | 答えの誤り、コンパイルエラー、基盤障害、表示通信の断を区別する。不正解では残りを続け、終了した実行を再び採点中に戻さない | B2、B3、B5、B6、WebUI |
| 混雑時にも合意した遅れで更新される | ケース完了数・保存回数・閲覧数を含む負荷の目標を決め、更新の蓄積や間引きを含めて設計する | B1、B2、B3、B5、B6 |
| 他の人に隠すべき情報を出さない | 閲覧時の認可と公開項目の制限をする。ケース数・途中得点も公開する情報に含めて判断する | B2、WebUI |

B5/B6からは実行で起きた事実を受け取り、B2が登録済みの解釈情報に沿って、ケースの判定完了や全体の進捗へ対応付ける。B6が全体の完了数を独自に集計したり、利用者のブラウザへ直接通知したりする前提は置かない。

## DAGのノード完了と、ケースの判定完了は別

1ケースに実行・出力確認など複数のノードが必要な場合や、準備・コンパイル・最終集計のノードがある場合を扱う。プロセスが正常終了しただけでは、そのケースの判定完了とは限らない。

- CLIの登録情報から、ケースの識別、表示に数える対象、判定完了を解釈する条件をB2が得られる必要がある。
- ケースごとの判定完了が、既存のノード結果から分かるなら、その結果から進捗を作る。
- 1ノード内で複数ケースを処理し、その途中を見せたいなら、途中の事実を報告できる必要がある。ノードを分けるか、ノード内の途中報告を追加するかは接続契約で検討する。
- 対象が事前に確定しない定義でも、ケースの判定完了が分かれば完了数を表示できる。総数も表示する場合は、確定するまで分母を示さない。ケース単位で数えられない問題の見せ方は別に決め、ノード数を代用してケース数と表示しない。

この対応は[問題登録・結果解釈の受け渡し仕様](14-specified-requirements/01-external-interfaces/problem-registration-contract.md)のCONTRACT-07/08につなぐ。途中報告を追加しても、実行要求の単位を変えることまでは意味しない。

## 通信形式を決める前に共有する例

以下は業務上の事実と表示の例。メッセージ名やフィールド名は確定しない。

| 順序 | 起きた事実 | B2/B3が持つべき状態 | 利用者の表示例 |
| --- | --- | --- | --- |
| 1 | 提出Sの採点R1を受け付けた | SとR1、採用版、待機状態 | 採点待ち |
| 2 | R1の対象がT1・T2・T3と分かった | 対象3件、完了0件。総数の公開は任意 | 採点待ち |
| 3 | R1の採点を開始した | R1が開始済み | 採点中・完了0件 |
| 4 | R1のT2の判定が完了した | 完了した対象はT2 | 採点中・完了1件 |
| 5 | R1のT1が不正解と判定された | 完了した対象はT1・T2。T3の実行を続ける | 採点中・完了2件 |
| 6 | T2の同じ結果が再び届いた | 完了した対象はT1・T2のまま | 完了2件のまま |
| 7 | 表示用の接続が切れた | 採点R1は継続 | 接続が切れたことと、最後に確認した完了2件 |
| 8 | 接続が切れている間にT3と最終集計が完了した | R1の完了状態と確定結果 | 切断中の画面では表示を更新できない |
| 9 | 利用者が開き直した | 保存済みのR1の結果を返せる | 確定結果を直接表示 |
| 10 | 別の採点R2を受け付けた | Sに対する別の実行として、R1とR2を区別 | R2を表示する場合は、R1と別の進捗として表示 |
| 11 | R1の古い通知が遅れて届いた | R2に混ぜず、確定済みのR1を巻き戻さない | R2の進捗を変えない |

再採点時にどの実行を代表表示するかは既存のMUT-05で決める。現在表示している実行と違う結果を、提出IDが同じという理由だけで混ぜない。

## 「都度表示」のどこまでを保証するか

次の2つは要求するものが違うため、選定前に分ける。

| 要求の候補 | 表示の例 | 実装への条件 |
| --- | --- | --- |
| 最新の進捗へ合意した遅れで追い付ける | 短時間に完了1件から完了5件へ進んだら、途中の描画をまとめてもよい | ケースの結果を正しく保存し、最新状態を再取得できる。更新の集約が可能 |
| 全ケースの完了を1件ずつ通知・描画する | 完了1件、2件、3件をすべて受け取って見せる | 通知の履歴・順序・再開位置、遅い閲覧者に対する蓄積上限を決める。画面への反映速度も制約になる |

どちらの場合も、ケースごとの業務結果を重複して数えてよいことにはならない。最新状態を再取得できることと、過去の全通知を再送できることは別の要件。ブラウザを閉じていた間の全件を再生するかも別に決める。

## 全ケースを継続する条件と、障害の扱い

| 起きたこと | 決めること | 基盤へ渡す条件 |
| --- | --- | --- |
| あるケースが不正解・時間切れになった | 全ケースを続けることは確定済み | そのケースを完了として記録し、B2は残りのケースを継続する。B6のプロセス終了・時間制限と、ケースの判定結果の対応を定義する |
| コンパイル不能や実行基盤の故障で、全ケースを実行できない | 復旧・再試行・終了と、未実行ケースの見せ方 | 不正解・時間切れによる打ち切りとは区別する。未実行のケースを完了数に含めない |
| あるノードの試行をやり直す | 再試行中の見せ方と、採用する試行 | 同じケースを二重に数えない。古い試行の遅着で、採用済みの状態を上書きしない |
| 実行から長時間知らせが来ない | 長い処理、混雑、障害をどう判別するか | 経過時間だけで不正解にしない。監視の基準、タイムアウト、必要なら生存確認の報告を設計する |
| 利用者が取り消したい | 取り消し操作を提供するか | 採用する場合のみ、B2による許可と、未開始・実行中・終了済みそれぞれの停止条件が必要 |

ケースの時間切れは判定結果、計算ワーカーの障害は実行基盤の失敗、ブラウザの切断は閲覧経路の失敗として区別する。待機列での順位や残り時間の予測を表示する要求は、今回の進捗表示には自動で含めない。

## 遅延と容量を決めるための項目

数値は現時点では未決。構成を選ぶ前に、平常時・大会開催時・一括再採点時それぞれで次を埋める。

| 項目 | 何に効くか |
| --- | --- |
| ケース判定完了から画面反映までの遅延目標 | 実行基盤からの報告、APIの受理・保存、WebUIへの更新それぞれの遅延配分 |
| 提出数/秒と、1提出のケース数・ノード数 | 完了報告の発生量、DB更新量。まず提出数×ケース数でケースの更新量を見積もり、ノード数・開始報告・再試行分を加える |
| 同時に見る人・画面・提出の数 | 取得要求や接続の数、同じ進捗を複数の閲覧者へ渡す量 |
| 1回で返す内容 | 件数だけか、全ケースの一覧か。毎回全件返す場合の応答量 |
| 保存期間と再接続の保証 | 最新状態、ケース結果、通知履歴それぞれの保存量と、復元できる期間 |
| 一括再採点の対象数と同時実行の扱い | 通常提出の待ち時間、更新報告の集中、基盤と閲覧側への負荷 |
| 更新が集中したときの扱い | 表示更新の集約を許すか、遅い閲覧者をどう扱うか。最終結果まで捨ててよいとはしない |

通信手段やAWSの具体的なサービスは、これらの条件と[B0〜B6の接続](../services/aws-building-blocks.md)を揃えてから選ぶ。

## 現在のコード・API資料との差

- [単独提出の採点状態](../../server/traojudge-core/src/domain/model/judge_state/single_player.rs)には `progress_now` / `progress_full` があるが、ケース完了数なのか、どの事実で更新するかの定義はない。
- [提出・採点のモデル](../../server/traojudge-core/src/domain/model/submission.rs)では、採点状態や進捗の項目にTODO・コメントアウトが残っている。型があるだけで、このシナリオが実装済みとは扱わない。
- [OpenAPI 3.1.1の契約案](../API/front_back.yaml)では、実行ごとの取得応答に `completedCaseCount`、任意に公開する総数、状態の版、確定結果を分けて定義した。ケース名・入出力・個別判定はこの進捗応答に含めない。旧OpenAPIは置き換え、`judgeProgressStep` を新しい契約へ引き継がない。

表示と基盤の制約を基にOpenAPIの契約案を追加した。UI・ハンドラーの実装と、内部メッセージ形式の確定は別に行う。

## 担当ごとに先に実装できる終点

| 作業 | 他の担当の実装を待たずに確認すること |
| --- | --- |
| WebUI | 上の時系列を与え、進捗・切断・再取得・確定結果・別の再採点を混ぜずに表示する |
| B2 API | ノード結果とケースの対応例から進捗を作る。重複・遅着・終了後の通知を与えても件数や状態を壊さない |
| B3 保存 | ケース結果と公開する状態を整合して保存でき、再起動後・別プロセスからも再取得できる |
| B5/B6 通信・実行基盤 | ケースの途中経過に必要な事実を、全体終了前に報告できるかを固定した実行例で確認する。具体的な形式は後で合意する |
| CLI・定義 | 3ケースと、コンパイル・実行・確認・集計のノードを含む例で、ケース完了をAPIが解釈できる情報を提示する |

## 先に決めること

1. 完了数に加えて、総数やケースごとの判定まで見せるか。全通知の受信・描画まで必要か。
2. ケースの識別と判定完了を、登録された定義からどう決めるか。
3. コンパイル不能や実行基盤の故障時の、復旧・再試行・終了の条件。
4. 誰にどの途中情報を見せるか。
5. 更新の遅延目標、負荷の条件、復元できる期間。

これらを[実装メモのMUT-10](scenario-implementation-notes.md#作業票の形式と未決事項)として追う。
