# Judge VM pool policy

The current contract is **one execution/node per VM at a time**, with normal pool scheduling configured to target zero through five VMs. A warm VM may execute many nodes or submissions sequentially, after sandbox and work-directory cleanup succeeds. There is no multi-slot host mode.

The source of policy is [`infra/policy/pool.json`](../../infra/policy/pool.json). Its [JSON schema](../../infra/policy/pool.schema.json) defines the document shape; [`runtime/policy.py`](../../infra/runtime/policy.py) validates cross-field constraints and implements pure target/retirement decisions without AWS dependencies. CDK invokes this compiler at synthesis and supplies the exact compiled JSON to every runtime and host as `POOL_POLICY`. CloudFormation outputs include its selected profile and SHA-256 fingerprint. No deployment or AWS outcome is implied by this document.

Select `--context poolProfile=lookahead` (default) or `--context poolProfile=reactive`; `--context poolProfile=prewarmed` retains five warm VMs for a separately measured prewarmed operating condition; `--context poolPolicy=<path>` selects a separately reviewable document. Profiles choose strategy, operating limit, and warm count; timers and retry bounds are shared document fields. A new experiment can supply a separate policy document. Old `poolMax`, `nodeVisibility`, `nodeAttempts`, and `idleSeconds` context knobs are rejected. The capacity API rejects runtime configuration changes: policy changes require a reviewed CloudFormation deployment.

## Demand and cost bounds

The reactive profile uses queued/in-flight node counts, projected ready/starting/running graph nodes, current active hosts, and control work. SQS approximate counts overlap graph counts, so the controller takes their maximum rather than summing them. The lookahead profile additionally sums per-run peak projected execution demand. Every execution needs its own VM; target capacity is capped by the profile operating limit and the immutable ASG maximum of five. Placement is declared in the policy: one AZ/subnet, with replacement minimum healthy percentage zero and maximum 100. CDK applies this as the ASG instance maintenance policy, selecting terminate-before-launch replacement rather than adding temporary healthy capacity. Single-AZ placement avoids cross-AZ rebalancing for this experiment. These choices trade availability and replacement speed for a tighter normal pool capacity bound; they are not a production availability recommendation. They do not create a global invoice cap, bound other AWS resources or accounts, or provide absolute physical-instance-count guarantees under EC2/control-plane failure or external administrative actions.

The graph projection traverses dependencies using full wall-limit durations and assumes unresolved gates pass. It measures the peak earliest-start overlap within the configured 240-second horizon. Failed/cancelled ancestors prune descendants. Completed nodes contribute no remaining duration. Sequential chains peak at one. Independent or future case branches can request capacity before they become ready, and failing a gate can therefore leave provisioned VMs idle. This is a modeled all-success scenario, not a mathematical upper bound on demand within the horizon: a gate may finish earlier than its wall limit and expose branches that the modeled schedule places beyond the horizon. Summed per-run peaks can also overestimate simultaneous demand because the peaks need not occur together. This is neither an arrival predictor nor a probability/boot-time simulation. Queue length alone cannot expose this future demand.

The default profile retains one warm VM until explicitly asked to sleep. After sleep, the next wake keeps one warm for the document's idle interval; each receipt wakes capacity. Reconciliation also runs every minute. The only admin actions are `reconcile`, `wake`, and `sleep`. Sleep rejects observed queued/in-flight, active, control, or projected work. An operator must quiesce admission before using sleep as a shutdown request: queue statistics, demand records, and new submissions are not one transaction.

## Declarative scaling and drain

The controller publishes `SafeDesiredInstances`; only CloudFormation-declared CloudWatch alarms and exact-capacity ASG step policies change desired capacity. Its IAM role cannot call `SetDesiredCapacity` or `UpdateAutoScalingGroup`. One nonzero policy contains exact-capacity bands for every integer from one through the declared maximum; a separate alarm/policy requests zero. A 0.5 threshold and integer values produce the corresponding exact target. Estimated instance warmup is explicitly zero. Simple-scaling cooldown does not apply to StepScaling; the controller's own scale-in waiting period is a separate policy field. This custom metric controller is still application code, with its decisions isolated as pure policy functions; it is not a managed AWS workflow scheduler.

Metrics use 60-second `Maximum`, one evaluation period, and missing data `NOT_BREACHING`. The controller publishes on work transitions and scheduled reconciliation. A failed publisher does not publish zero. Older high samples delay reductions; asynchronous alarm actions and Auto Scaling reconciliation add latency, and a prior alarm may still act after a new controller decision. Missing metrics establish no scale-in permission; an existing valid low sample can continue an already authorized retirement. There is no claim of instantaneous target convergence or bounded response under AWS/control-plane failure.

New VMs start protected from scale-in. The controller records a per-instance irreversible retirement token durably before publishing a drain command. The host persists that token on disk before unprotecting itself, closes new poll reservations, waits for any already reserved receive and its admitted execution including cleanup, and acknowledges the token in its heartbeat. Only a fresh matching `drained` heartbeat, explicit `active == 0` and `polling is False`, and observed ASG unprotection permit the controller to lower its metric. The controller checks these independently; a missing polling field fails closed. Unknown, pending, stale, or quarantined hosts cannot acknowledge drain. If there is no eligible retirement candidate or existing retirement, a lower target holds the current metric with `await_unknown_capacity`; ASG protection remains an independent fence. Poll reservation and drain share a lock: a receive admitted before drain may return one message and execute it while still protected. The agent never unprotects with a pending poll or active execution/cleanup, and never requeues a valid reserved receive merely because drain arrived during the long poll. Heartbeats expose `polling`, `poll_started_at`, and active `admission`; attempts and new results record admission mode `reserved_before_drain` when this interleaving occurs. A receive error releases the local reservation; SQS can still have delivered an unseen response, so network failures and at-least-once delivery remain distinct retry causes.

**A drained VM never resumes.** Setting protection back to true cannot undo a termination already selected by an older alarm. Existing retirements therefore finish before a demand rebound requests replacement VMs. This trades extra cold-start delay for a verifiable fence: late low alarm actions can terminate only idle retired hosts, while active/queued-capable hosts stay protected. The retirement marker survives agent restarts; the controller can redeliver a command to a restarted agent. There is no per-VM multiple-worker thread pool.

## Retry, reuse, and recovery boundaries

Node delivery uses the policy's visibility duration, renewal interval, and receive-count limit followed by NodeDLQ. The renewal interval must allow at least two renewal attempts per visibility window. A host persists the result before sending completion and deleting its node message. Re-delivery resumes from that durable result; it does not claim exactly-once execution. Unique artifact attempt paths and conditional result writes make duplicate attempts observable. Control delivery has its own FIFO/DLQ path. A DLQ result is an infrastructure failure, not a contestant verdict. Fault-injection receipt fields are confined to this IAM-protected infrastructure experiment fixture.

Before reuse, the host removes its sandbox, proves its absence, removes the working directory, and records a cleanup object. Agent startup removes predecessor sandboxes/directories before consuming. Any cleanup failure quarantines the host; it cannot execute again or acknowledge safe drain. Loss of heartbeat/control connectivity stops new claims. EC2 host loss can be replaced by ASG health while SQS retries work. Scale-in protection does not stop EC2 health replacement, host faults, Spot interruption, or external administrative termination.

A boot-stuck, quarantined, or agent-dead VM can consume capacity indefinitely while protected. Automatic application-health replacement is not implemented. Adding a CloudFormation-managed watchdog/lifecycle recovery policy is separate work; the current controller fails closed rather than unprotecting an unknown host. Demand projections expire and are repaired by work transitions, not periodic checkpoint reconstruction. A missed transition plus stale SQS counts may temporarily under-estimate demand. DynamoDB scans and per-host S3 heartbeats are bounded demonstration adapters, not a production high-volume index. No fairness, admission quota, contest scheduling, autoscaling budget dollars, or production SLO is established here.

## Verification

`python infra/scripts/check-pool-policy.py` exercises policy bounds/profile differences, gated future demand, failed ancestry, deep graphs, sequential boundaries, matching drain tokens, protection checks, demand rebound, and host persistence/poll-reservation fencing. Host tests require the repository's boto3 environment but make no AWS calls. CDK type checking and synthesized-template inspection establish declared resources and permissions; they do not establish real scaling behavior. The parent experiment report records actual AWS measurements separately and must include the policy fingerprint and teardown evidence.
