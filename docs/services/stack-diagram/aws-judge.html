02 二部DAG：ファイルと実行が交互に並ぶ
ファイルの依存を実行の依存へ縮約する
compile → binary → run は、Jobの compile → run になる。
Artifact = 名前付きファイル　　Execution = 入出力・起動処理の定義　　Job = Engineが保存・状態管理する実行単位
上段はデータの依存。下段はそこから導いたJobの起動順。
ArtifactにはJobを作らない。中間ファイルは生成元が1つ。起動スクリプトも通常のArtifactであり、問題定義全体とは区別する。
03 制御メッセージとファイル転送を別のレーンで読む
1　要求 →　1つのExecutionを起動
2　← 結果　ファイル保存後に通知、永続受理後にack
3　ファイル内容 →　SQSを通らず、WorkerだけがS3と転送
mainのstdout JSON と生成ファイルは別。 後段で計算に使うscore等はArtifactとして宣言する。
同名のController / Workerは同じプロセスをレーンごとに再掲。
WorkerがS3へ保存 → 結果参照をSQSへ送信 → ControllerがDBへ受理・適用 → その参照を使って次のTaskを送る。
04 対話は1つのExecution内部のFIFOセッション
ONE Execution / session: each process is a separate container
main container / private judge inputs
peer container / submission inputs
許可入力　judge script + 非公開データ
許可入力　提出 + 起動script
Workerが回収・転送： main stdout → 結果JSON、main outputs → S3。transcript / replayの生成元はmain。
全コンテナ共通： network none / AWS資格情報なし / UID 65534 / read-only root / capability削除 / no-new-privileges
CPU・メモリー・PID・wall time・出力サイズを制限。Docker socketは渡さない。
FIFOの双方向通信はDAGの辺にしない。DAGは完成したファイルの依存だけ。
coding-gameはpeerを複数持ち、各peerに専用のFIFO対を用意する。コンテナはホストkernelを共有する。
05 同じファイル／実行モデルで構成する判定方式
通常判定
Cをコンパイルし、20+22の出力42を確認する。
heuristic
独立試行のscoreファイルを集約する。seed 0/1の平均得点は33.0。
run-twice
sandboxを作り直し、宣言したstateだけを次の実行へ引き継ぐ。
interactive
dialogueの内部でinteractorと提出を別sandboxに置く。21→42の会話。transcriptはmainが生成する。
coding-game
refereeと2提出を別sandboxに置く。a=4 / b=5、勝者b。replayはmainが生成する。
方式ごとにDAGの基本型を増やす必要はない。対話・対戦の違いは実行内のsession契約、得点や判定の意味は作問側の処理が担う。
